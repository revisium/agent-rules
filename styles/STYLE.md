# Writing style

Apply this guide when writing or editing prose in project artifacts, including
PR titles and bodies, issues, commit messages and documentation. The shared
AGENTS.md defines the default language; applicable local language overrides and
explicit user instructions select the language for each output. This guide
controls style and does not change that selection.

## Common rules

- Write in a neutral professional tone for a colleague who must make a decision
  or implement the system. Lead with the concrete problem, decision or result.
- Each sentence communicates a fact, decision, requirement, constraint or
  consequence. Each paragraph develops one idea.
- Name the actor: the user, system or relevant role. Prefer active verbs.
- Replace evaluative words with observable behavior or a measurable criterion.
- Distinguish hypotheses, accepted decisions, requirements and open questions.
- Use the same term consistently. Explain unfamiliar technical terms on first use.
- Use headings that identify the subject. Replace template questions and prompts
  with concrete facts before review.
- State expected behavior directly. Avoid promotional language, filler, repeated
  conclusions and rebuttals to alternatives the reader has not raised.
- Preserve identifiers, JSON fields, error codes, protocol names, commands, logs,
  technology names and quoted source text. Follow the project's glossary for
  product concepts; follow product locale requirements for interface copy.
- Use code formatting for an exact interface label when the string is part of
  the UX contract. Otherwise describe its meaning and keep final copy in the
  implementation or localization catalog.

## Before handoff

Read the whole output. Check the intended language, genre, consistent terminology,
absence of repetition, working links, numbering where applicable and removal of
placeholder text. Use the repository's templates for document structure.
